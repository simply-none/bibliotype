## 产品概述

文档承接 `能力扩展清单.md` 的「能力地图」，只回答「怎么排期、怎么拆、怎么验收」，不重复抄写能力定义；同时把核查中发现的 7 处清单与代码偏差记录在案，作为后续回写依据。

- **总览台账**：52 项 × 编号 / 名称 / 能力域 / 当前状态 / 前置依赖 / 工作量（S/M/L）/ 所属批次。

## 验收标准

- 52 项编号与 `能力扩展清单.md` 严格一一对应，无遗漏、无重复、无新增臆造项。
- 每条证据路径与符号均可在当前仓库命中；不写入未经核实的 API。
- 文档自身可独立执行：任一 checkbox 都能直接对应到具体文件与验证方式。
- 不修改任何代码、配置、既有清单。

## 技术方案

### 写作依据

- 事实来源仅为上一轮逐项核查结论（导出符号、文件路径、测试存在性），不重新推断、不夸大。
- 能力定义与优先级理由引用 `能力扩展清单.md` 的编号，避免两份文档各写一套描述而漂移。
- 排版沿用仓库既有清单风格：`# 标题` → `> 依据/范围/约定` 引用块 → `## 一、二、三` 或 `P0/P1` 分节 → 表格 + `- [ ]` 复选框。

### 文档结构

1. 头部：分析基准日期、核对方式、统计口径、与 `能力扩展清单.md` / `功能完善增改清单.md` 的分工。
2. 进度总览：52 项按批次汇总的数量表 + 分阶段 checkbox。
3. 总览台账表：`编号 | 名称 | 域 | 状态 | 前置 | 工作量 | 批次`。
4. P0–P4 明细：每项统一模板（目标 / 现状证据 / 前置 / 工作量 / 工作分解 / 验收 / 涉及包）。
5. 依赖关系：文字版链式说明（`A → B`），不引入图工具。
6. 清单偏差修正表：7 条，标注「建议回写 `能力扩展清单.md`」。
7. 暂缓项索引：一句话指向既有清单 20 项，不展开。
8. 执行约定：完成定义、验证命令（`pnpm test` / `pnpm typecheck` / 文档链接检查）、提交信息格式。

### 工作量与批次口径

- S：单文件小改或纯配置；M：跨 2–3 个包；L：新包或跨 5 个以上文件/需新测试基建。
- 批次按「依赖优先 + 投入产出」排序，I1/I3/I4/I9 等护栏项允许与 P0 并行插入，不阻塞主线。

### 质量校验

- 用编号清单逐条比对：26 个 `[ ]` + 26 个 `[~]` 全部出现在台账且各出现一次。
- 证据路径统一写相对路径 + 符号名；写入前抽查存在性，避免死引用。
- 内部链接只指向已存在文件（`docs/02`、`docs/04`、`docs/05`、`docs/07`、`docs/17`、`docs/18`、`docs/21`、`docs/23`–`docs/31`、两份既有清单）。

### 执行注意

- 不把 P0–P4 写成「承诺工期」，只给相对工作量与建议顺序，避免与实际排期冲突。
- 部分完成项必须写清「已有什么、只差什么」，防止执行时重复造轮子。
- 涉及新包的条目（`exporter-docx`、`adapter-sqlite`、`provider-websocket`）需在条目内注明包名、依赖方向与 `pnpm-workspace` 注册要求。
